# Контрольные сценарии

Сценарии описывают способы повторной проверки своего стенда. Приведённые команды составлены при оформлении репозитория и не являются сохранённой историей исходного эксперимента. Временные метки, event/rule ID и уровни алертов автора не предоставлены; значения не выдумываются.

Перед проверкой записать время, часовой пояс, имя/ID агента. В Dashboard выбрать корректный временной диапазон и агента. Интерфейс разделов может отличаться между релизами.

## 1. События SSH

**Цель:** сопоставить попытку входа на Astra Linux с записью в журнале и событием в Wazuh.

На собственной ВМ с работающим SSH выполнить один вход с административного клиента:

```bash
ssh LAB_USER@ASTRA_AGENT_IP
```

Для проверки отказа можно один раз ввести неверный пароль своей тестовой учётной записи, если сервер использует парольную аутентификацию; не менять настройки аутентификации только ради этого сценария. При входе только по ключу этот вариант не применяется. Успешный и неудачный вход — разные результаты, фиксировать реально полученный.

На Astra Linux сопоставить время в `/var/log/auth.log`; затем найти событие в Threat Hunting по агенту и времени. В исходном описании SSH-события наблюдались в Linux-журнале и Dashboard; точный тип входа и rule ID не указаны.

**Что сохранить:** действие, время, источник/узел назначения, текст события с обезличиванием, rule ID и уровень только из фактического алерта. Если есть лишь локальная запись — это ещё не подтверждение доставки в Wazuh.

## 2. Использование sudo

На Astra Linux, под своей учётной записью:

```bash
sudo -k
sudo /usr/bin/id
```

Команда `sudo -k` сбрасывает кеш учётных данных текущего пользователя; следующая команда может запросить пароль. `id` только выводит идентификаторы, не меняет пользователей и права. Затем сопоставить запись sudo в журнале и событие в Dashboard.

По описанию регистрация sudo проверялась; точный алерт и скриншот не переданы. Не приписывать этому сценарию обнаружение повышения привилегий эксплойтом: здесь используется штатный `sudo`.

## 3. Контроль целостности файлов — FIM

**Предусловие:** каталог `/opt/siem-fim-test/` существует и включён в действующую конфигурацию FIM. Пример `syscheck` — [здесь](../configs/examples/fim-syscheck.fragment.xml). После настройки дождаться начального сканирования; существование файла на момент базового сканирования само по себе не является событием его создания.

Пример ручного теста на собственной ВМ:

```bash
sudo mkdir -p /opt/siem-fim-test
# Выбрать уникальное имя. Убедиться, что такого файла ещё нет.
FIM_FILE="/opt/siem-fim-test/portfolio-$(date +%s)-$$.txt"
sudo test ! -e "$FIM_FILE"
# Продолжать, только если предыдущая команда завершилась с кодом 0.
printf 'Wazuh portfolio FIM test\n' | sudo tee "$FIM_FILE" >/dev/null
```

Сохранить результат создания. Затем в том же терминале выполнить изменение:

```bash
printf 'Modified during FIM test\n' | sudo tee -a "$FIM_FILE" >/dev/null
```

После фиксации результата удалить только созданный тестовый файл:

```bash
sudo rm -- "$FIM_FILE"
```

Между действиями дождаться соответствующего события: быстрые последовательные изменения могут объединиться или наблюдаться иначе. При scheduled-режиме ждать настроенного интервала; для realtime проверить поддержку и работу мониторинга. Не заменять отсутствие события вымышленной записью в отчёте.

**Что сохранить для каждого этапа:** время, путь, операция (создание/изменение/удаление), агент, rule ID/уровень из реального события. По исходному описанию действия с файлами выполнялись, но отдельное подтверждение алерта каждой операции пока отсутствует.

## Запись результата

В [реестре доказательств](../evidence/manifest.csv) указать статус и относительный путь к обезличенному скриншоту/выдержке. Если сценарий не сработал, записать фактическое наблюдение, диагностику и повторную проверку. Повторяемость важнее формулировки «всё работает».
